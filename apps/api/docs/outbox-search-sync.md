# 검색 동기화(Outbox → RabbitMQ → Elasticsearch) 설계

기록(Record)의 변경을 Elasticsearch에 반영하는 비동기 파이프라인의 **중복 · 순서 · 장애 복구** 설계와 그 근거를 정리한다.

## 1. 전제: 최소 한 번(at-least-once) 전달

Outbox 패턴과 RabbitMQ는 메시지를 _최소 한 번_ 전달한다. 즉 아래 상황에서 같은 이벤트가 **여러 번**, **순서가 뒤바뀌어** 도착할 수 있다.

- 발행은 성공했지만 `DONE` 기록이 실패해 다음 주기에 재발행
- 컨슈머가 처리 중 크래시/재시작해 재전달
- 일시 장애로 재시도(재발행)되는 사이 뒤 이벤트가 먼저 처리

따라서 "메시지를 정확히 한 번 보낸다"가 아니라 **"여러 번, 뒤섞여 와도 최종 상태가 같다"**를 목표로 설계했다.

## 2. 변경 전 문제

| #   | 문제                                                                                        | 영향                                  |
| --- | ------------------------------------------------------------------------------------------- | ------------------------------------- |
| 1   | 중복·지연 이벤트가 ES 상태를 과거로 되돌림 (`CREATED`는 전체 덮어쓰기, `eventId`는 로그용)  | 즐겨찾기·연결 수 등이 옛 값으로 롤백  |
| 2   | 순서 보장 없음 (퍼블리셔는 실패를 건너뛰고 계속 발행, 컨슈머는 `prefetch 10`으로 동시 처리) | `UPDATED`가 `CREATED`보다 먼저 도착   |
| 3   | `update` 404가 `nack(requeue)`로 무한 재큐잉, 재시도 상한·DLQ 없음                          | 삭제된 문서에 대한 이벤트가 영구 루프 |
| 4   | Outbox `retryCount`가 증가하지 않아 `DEAD`로 전환 불가                                      | 영구 실패 이벤트가 5초마다 재시도     |
| 6   | `RECORD_UPDATED`가 `connectionsCount`를 0으로 하드코딩                                      | 기록 수정 시 ES 연결 수 초기화        |
| 8   | 오리 컨슈머가 ES 동기화와 같은 큐·ACK에 편승, Redis `incr`가 비멱등                         | ES 재시도마다 카운트 중복 증가        |

(5번 "다중 인스턴스 중복 발행"은 단일 인스턴스 전제로 한계에 남긴다. §7 참고.)

## 3. 설계

```
[기록 변경 트랜잭션]                       [OutboxPublisher: 5초 주기]
 record 변경                                PENDING/RETRY 조회
 + buildSnapshot(tx)  ──▶ outbox row ──▶   record.sync.queue ──▶ RecordSyncConsumer ──▶ ES
   (완전한 스냅샷)        (같은 트랜잭션)    duck.record-created.queue ─▶ DuckConsumer ──▶ Redis
                                            (RECORD_CREATED만)
                                            모두 성공해야 DONE, 실패 시 retryCount++ (5회 → DEAD)
```

### 3.1 발행: 항상 "완전한 스냅샷"

- 삭제를 제외한 모든 이벤트(생성/수정/즐겨찾기/연결 수)는 변경이 반영된 **같은 트랜잭션 안에서** `RecordSnapshotService.buildSnapshot`으로 기록 전체 상태를 만들어 Outbox에 싣는다.
- 레코드 행 락을 쥔 채 읽으므로 변경과 스냅샷이 정확히 일치하고, 같은 기록의 outbox id 순서가 커밋 순서와 일치한다.
- 컨슈머는 DB를 다시 읽지 않는다. 읽기 비용이 _전달 시점_(재전달마다)이 아니라 _변경 시점_(1번)으로 이동한다.

### 3.2 소비: outbox id를 ES external version으로

- `eventId`(= outbox id, 단조 증가)를 ES `version_type=external`로 사용해 `index`(전체 교체)한다.
- ES는 `version > 현재 버전`일 때만 쓰기를 허용하고, 아니면 409를 준다. 컨슈머는 409를 **오류가 아닌 "이미 반영됨(STALE)"으로 ACK**한다.
- 결과적으로 중복·지연·역순 이벤트가 어떤 순서로 와도 **최종 상태는 가장 높은 버전의 스냅샷**이다. 그래서 순서 보존 로직(같은 aggregate 보류 등)이 필요 없다.
- 삭제는 `delete` + 같은 버전으로 처리한다. 문서가 없어도(404) **삭제 버전(tombstone)이 기록**되어, 이후 도착하는 낮은 버전의 생성/수정이 문서를 되살리지 못한다.
- ES `update` API는 external version을 지원하지 않으므로 부분 업데이트 경로를 없애고(→ 404 루프도 사라짐) 전체 덮어쓰기 한 가지 경로만 남겼다.

### 3.3 장애 복구

- **Outbox**: `markPublishFailed`가 `retryCount`를 올리고 5회째 `DEAD`로 전환. 발행 성공 후 `DONE` 기록 실패는 "발행 실패"로 세지 않고 재발행(중복은 컨슈머가 흡수).
- **컨슈머**: `RmqRetryService`(큐 무관 공용 헬퍼)가 실패 메시지를 `x-retry-count`를 올려 지수 백오프(1s→30s 상한)로 같은 큐에 재발행하고, 5회를 넘으면 `<큐>.dlq`로 이동. 형식 오류(잘못된 `eventId`, 알 수 없는 이벤트 타입)는 재시도 없이 즉시 DLQ.
- 새 메시지가 브로커에 **확정(confirm)된 뒤에만** 원본을 ACK한다. 재발행/DLQ 발행이 실패하면 원본을 `nack(requeue)`로 되돌려 메시지를 잃지 않는다.

### 3.4 오리 코멘트 큐 분리

- 오리 갱신은 `duck.record-created.queue`(전용 큐·패턴)로 분리했다. ES 동기화의 실패·재시도가 오리 카운트를 중복으로 올리지 않고, 오리 처리 실패가 ES 동기화를 막지 않는다.
- 퍼블리셔는 `RECORD_CREATED`를 두 큐에 모두 발행하고 **둘 다 성공해야 `DONE`**. 한쪽만 성공한 채 재시도되면 성공한 쪽에 중복이 가지만 두 컨슈머가 멱등이라 안전하다.
- `DuckService`는 이벤트 ID를 Redis `SET NX EX`(24h)로 선점해 같은 이벤트의 카운트를 한 번만 올린다. 카운트 단계가 실패하면 선점을 풀고 재시도되게 하고, 카운트 이후의 멘트 갱신 실패는 재시도하지 않는다(다음 기록 생성 때 재갱신).

## 4. 검토한 대안

|                | A: 컨슈머가 DB 재조회              | **A′: 발행 시 완전한 스냅샷 (채택)** | B: payload 유지 + painless 스크립트                        |
| -------------- | ---------------------------------- | ------------------------------------ | ---------------------------------------------------------- |
| 중복·지연·역순 | 안전                               | 안전                                 | 부분 이벤트가 문서보다 먼저 오면 문제                      |
| DB 조회        | 전달될 때마다                      | 변경당 1번                           | 늘지 않음                                                  |
| 컨슈머         | DB 의존                            | ES 쓰기만                            | 이벤트별 분기+스크립트                                     |
| 한계           | 읽기/쓰기 사이 경쟁(버전으로 방어) | 쓰기 경로 쿼리 추가, Outbox 행 증가  | "생성 전" vs "삭제 후" 404 구분 불가 → 유령 문서 또는 유실 |

B는 부분 `update`가 external version을 못 쓰는 근본 한계가 있고, A는 A′보다 DB 부하와 경쟁 구간이 크다.

## 6. 변경 이력(커밋)

1. Outbox 발행 실패 `retryCount` 증가/`DEAD` 전환
2. `RecordSnapshotService` (스냅샷 빌더)
3. 발행 지점 전환(+ `connectionsCount: 0` 버그 해결)
4. ES external version 쓰기 + 컨슈머 단일 경로
5. `RmqRetryService`(재시도 상한·DLQ)
6. 오리 큐 분리 + 이벤트 ID 멱등
7. 죽은 코드 정리 + 이 문서

## 7. 한계와 운영 메모

- **삭제 버전은 `index.gc_deletes`(기본 60초)만 기억**한다. 그보다 훨씬 늦게 도착한 옛 `CREATED`/`UPDATED`는 삭제된 문서를 되살릴 수 있다(실제로 `gc_deletes=1s`로 재현함).
- ES 백필(`bulkUpdate`, 매핑 필드 추가 시)은 `update` 연산이라 문서 버전을 1 올린다. 같은 기록의 다음 이벤트 ID가 정확히 그 값이면 한 건이 STALE 처리될 수 있다(다음 이벤트로 수렴).
- 단일 인스턴스 전제: `isProcessing`은 프로세스 내부 플래그다. 다중 인스턴스에서는 같은 Outbox 행을 중복 발행할 수 있으며(컨슈머 멱등으로 안전) 확장 시 `FOR UPDATE SKIP LOCKED` 선점이 필요하다.
- 백오프를 `setTimeout`으로 기다리는 동안 메시지는 unacked로 `prefetch` 슬롯을 점유한다. 정석은 TTL 지연 큐다.
- DLQ(`record.sync.queue.dlq`, `duck.record-created.queue.dlq`)를 재처리하는 도구는 아직 없다. 현재는 RabbitMQ 관리 UI에서 확인·수동 이동한다. DLQ 메시지에는 `x-original-queue`, `x-retry-count`, `x-error`, `x-failed-at`가 남는다.
- Outbox 행이 스냅샷(본문 포함)을 담아 커지고, `DONE` 행 정리는 별도 과제다.
- **배포 주의**: 기존 ES 문서는 내부 버전을 가져 external version과 충돌할 수 있으므로 인덱스 재생성이 필요하다. `record.sync.queue`에 남은 구 형식(부분 payload) 이벤트와 구 오리 이벤트는 처리되지 않으므로 큐를 비우거나 이행 기간이 필요하다.
- `notification.consumer.ts`에도 같은 `nack(requeue: true)` 패턴이 남아 있다(이번 범위 밖).
